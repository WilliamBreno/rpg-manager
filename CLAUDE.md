**Manutenção deste arquivo:** sempre que um trabalho nesta sessão alterar algo que uma seção abaixo descreve (arquitetura, comandos, comportamento das edições 4e/5e, camadas, deploy, etc.), atualize a seção correspondente antes de considerar a tarefa concluída — não crie um changelog separado; o histórico de mudanças já vive no `git log`.

## Project overview

RPG Manager is a character sheet manager for tabletop D&D that supports **two editions side by side: 4e and 3.5/5e**. A character's `Edition` field ("4e" or "5e") drives which rules, fields, and calculations apply throughout the backend — this is the central architectural fact of the codebase. There are three independent apps in this repo:

- `backend/` — Go + Gin + GORM REST API (the core app, port 8080)
- `frontend/` — React 19 + TypeScript + Vite SPA (port 5173)
- `ai-service/` — Python FastAPI microservice (port 8000, **local-only, not deployed anywhere**) that RAG-queries indexed D&D rulebook PDFs via ChromaDB + Ollama to auto-generate class powers/skills and indexes 5e rulebook knowledge separately. It used to also fill the official 5e character sheet PDF for export, but that step now happens inside `backend/` itself (`internal/pdfexport`, pure Go, no external service) — see the PDF export section below for why

Comments, error messages, and commit messages in this codebase are in Portuguese; keep new ones consistent with that.

## Commands

### Backend (Go)
Run from `backend/`:
```
go run cmd/api/main.go     # start API server on :8080
go build ./...             # compile everything
go vet ./...                # lint
go test ./...                # run tests (no test files currently exist)
```
Requires a Postgres database and a `.env` file (see `backend/.env`, gitignored) with `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `SERVER_PORT`, `JWT_SECRET`. On every boot, `main.go` calls `config.ConnectDatabase()` (GORM `AutoMigrate`) followed by `seed.Run(db)`, which is idempotent (upserts) and repopulates classes/races/skills/pericias/talentos — expect this to run on every local start.

### Frontend (React/Vite)
Run from `frontend/`:
```
npm run dev       # start dev server on :5173
npm run build     # tsc -b && vite build
npm run lint      # eslint .
npm run preview   # preview production build
```
`VITE_API_URL` env var overrides the API base URL (defaults to `http://localhost:8080/api`).

### AI service (Python)
Run from `ai-service/`:
```
python main.py                 # or: uvicorn main:app --reload / python -m uvicorn main:app --reload (port 8000)
python ingest.py               # OCRs 4e PDFs from ai-service/books/ and indexes them into ./chroma_db (ChromaDB collection "dnd_books")
python rag_5e.py               # extracts text (no OCR) from a restricted page-range scope of the 5e Player's Handbook and indexes it into ./chroma_db_5e (custom store, NOT ChromaDB — see below)
python -m pytest tests/        # ai-service/tests/ — RAG 5e query test + PDF export integration test
```
Requires a local Ollama instance running the `nomic-embed-text` (embeddings) and `llama3.2` (generation) models, and Tesseract OCR installed (path is hardcoded in `ingest.py` for Windows, 4e pipeline only). `ingest.py`/`rag_5e.py` must be run once each before `/skills` or the 5e RAG functions (`rag_5e.query_5e`) return results. There is no `requirements.txt`; dependencies are `fastapi`, `chromadb`, `langchain-ollama`, `ollama`, `pytesseract`, `pillow`, `pymupdf`, `langchain-text-splitters`, `pypdf`, `pytest`, `numpy`.

`main.py` used to have no `if __name__ == "__main__":` block at all — running `python main.py` silently loaded the module and exited with code 0 without ever starting a server, no error printed. Anyone following the first documented command would get a dead service on port 8000 with no indication anything was wrong; the backend's PDF export (`POST /export/pdf/5e`) would then fail with a generic connection error, surfaced to the frontend user as "Não foi possível exportar a ficha em PDF" with no real diagnostic. Fixed by adding a standard `uvicorn.run(app, host="0.0.0.0", port=8000)` entrypoint at the bottom of `main.py` — `python main.py` now actually works as documented. If this regresses again, verify with `curl http://localhost:8000/health` right after starting it, not just by checking the process didn't crash.

**Why `rag_5e.py` does not use ChromaDB (important — don't "fix" this by switching it back):** `chromadb` 1.5.9's Rust-bindings `PersistentClient` has a real, reproducible local-persistence bug on Windows — `collection.add()` writes documents/metadata into `chroma.sqlite3` fine, but the HNSW vector index segment's binary files are never actually written to disk (only `index_metadata.pickle`, never the `.bin` files), so every later `.count()`/`.query()` on that collection raises `InternalError: ... Error loading hnsw index`. This was root-caused across three separate full re-ingestions, in this order of things tried and ruled out: concurrent access from a second process (ruled out — reproduced on a fully serial run), missing `client.close()` (added it — reproduced again anyway), `chroma vacuum --path` (ran clean, didn't fix it), restarting via `chroma run` as an HTTP server against the same directory (same error over `HttpClient`). This matches a known class of upstream issues (chroma-core/chroma Windows-specific HNSW persistence bugs). Worse, part of the un-compacted write-ahead-log data is **not recoverable** once `chroma vacuum` purges it — don't reach for `vacuum` as a repair tool for this failure mode, it doesn't help and can destroy the otherwise-recoverable WAL rows. The fix was to stop using ChromaDB for the 5e store entirely: `rag_5e.py` now keeps its own tiny store — `chroma_db_5e/embeddings.npy` (row-normalized float32 vectors) + `chroma_db_5e/metadata.json` (index-aligned list of `{documento, livro, edicao, categoria, pagina}`) — and does brute-force cosine search (`embeddings @ query_vector`) in `query_5e()`. At this scale (a few thousand chunks × 768 dims) that's exact and effectively instant; there was never a need for an approximate index here. The 4e pipeline (`ingest.py`, collection `dnd_books`) is untouched and still uses ChromaDB — it was built while an older chromadb version was installed and reads fine today, so there's no proven need to migrate it, but be aware the same bug would likely hit it too if it ever needed a fresh full re-ingestion under the currently-installed chromadb version.

**Ingestion scope is deliberately restricted, not "the whole rulebook":** an earlier pass ingested all 6 5e books cover-to-cover (~9.6k chunks) for a general-purpose AI knowledge base, per the original task brief. After the character-creation-completeness work (Talentos already existed; the Item/Armor shop catalog was added with real structured prices, not RAG-dependent), the user asked to narrow this down to just what's relevant to character creation and to *not* index general DM rules, creatures, or equipment (equipment now has its own structured catalog, see the Shop section below — it doesn't need RAG). `rag_5e.SCOPE` is a list of `(pdf_file, book_name, page_start, page_end, categoria)` page ranges — not whole books — currently just five ranges from `D&D 5.0 - livro-do-jogador-2024.pdf` (Criação de Personagens p.39-54, Classes p.55-182, Origens p.183-204, Talentos p.205-218, Magias p.241-375; ranges found via the `"CAPÍTULO N | ..."` headers PyMuPDF extracts). `categoria` here is one of `classes`/`talentos`/`magias`, not the old `regras`/`criaturas`/`classes` used in the whole-book pass. If asked to broaden this again (e.g. add Xanathar's extra subclasses, or go back to whole-book ingestion), extend `SCOPE` rather than reintroducing the old book-level `BOOK_CATEGORIES`/`EXCLUDED_BOOKS` approach — the page-range design is what let this be scoped down without restructuring the code.

Checking ingestion progress on `chroma_db_5e/` from another process is trivial and safe: it's just `len(json.load(open('chroma_db_5e/metadata.json')))`, no locking concerns. For the untouched 4e `chroma_db/chroma.sqlite3`, a read-only `sqlite3.connect('file:chroma_db/chroma.sqlite3?mode=ro', uri=True)` against the `embedding_metadata`/`segments`/`collections` tables is safe to inspect without going through the ChromaDB API.

## Architecture

### Backend layering
Strict `handler → service → repository → domain` layering, all wired manually (no DI framework) in `cmd/api/main.go`:
- `internal/domain/` — GORM models (`Character`, `Class`, `Race`, `Skill`, `Pericia`, `Talento`, `Antecedent`, `Background`, `Armor`, `Item`, `CharacterItem`, `CharacterArmorOwned`, `User`)
- `internal/repository/` — GORM queries, one file per entity
- `internal/service/` — business logic (edition-specific math lives here, see below)
- `internal/handler/` — Gin handlers, one file per entity, only parse/validate HTTP and delegate to services
- `internal/seed/` + `pkg/config/seed*.go` — large static data files (classes, races, skills, pericias, talentos per edition); `seed.go` alone is 300+KB, read it with `offset`/`limit` rather than in full
- `pkg/middleware/auth.go` — JWT bearer middleware, sets `userID`/`userRole` in Gin context
- `pkg/config/database.go` — Postgres connection + `AutoMigrate`
- `internal/service/pdf_export_service.go` — computes every value (mods, save/skill bonuses, AC, proficiency) needed to fill the 5e PDF sheet; `internal/pdfexport/` does no D&D rules math, it only maps those already-computed values onto AcroForm fields (see "PDF export (5e)" below — this used to be a Python service, now it's a Go package with the template embedded via `go:embed`)

Routes are registered in `main.go`: most reads are public, writes to `characters`/`classes`/`races`/`skills` and pericias/talentos-on-character are behind `AuthMiddleware`. Auth uses `Authorization: Bearer <jwt>`.

### Dual-edition logic (4e vs 5e)
`internal/service/character_service.go` is the heart of the ruleset differences — read it before touching any character math:
- Separate XP tables (`xpTable4e`, `xpTable5e`) and max level (30 vs 20)
- HP: 4e uses `BaseHP + CON` then flat `HPPerLevel` per level; 5e uses hit die + CON mod, half-die+1+CON mod per level
- 4e has Surge Value/Surges-per-day and four defenses (`Defense_AC/Fort/Refl/Will`, all `10 + level/2 + ability mod + class bonus`); 5e has `ProficiencyBonus` (scales by level breakpoints) and Death Saving Throws (`DeathSaveSuccesses/Failures`)
- ASI (Ability Score Improvement) levels differ: 5e is fixed levels {4,8,12,16,19}, 4e is every even level; `checkAndApplyLevelUps` auto-advances level-by-level on XP gain and pauses at ASI levels waiting for a player choice via `ApplyASI`
- At an ASI level, `ApplyASI` now enforces RAW's "attribute points OR a feat, never both": `ASIChoice.TalentoID *uint` is an alternate path — if set, all 6 attribute fields must be zero (else 400 "não é possível escolher atributo e talento na mesma melhoria"), the character's edition must be 5e (4e has no Talento-for-ASI trade), and the talento is granted via `TalentoRepo.Add` instead of touching any ability score. Frontend: the ASI modal (`CharacterDetail.tsx`) has an "Atributo"/"Talento" tab toggle, only shown for 5e characters. **Update: the gap above is closed.** `internal/seed/seed_talentos_5e.go` seeds the full 75-feat PHB 2024 Talentos chapter (10 Origem, 43 Geral, 10 Estilo de Luta, 12 Dádiva Épica), extracted verbatim from `ai-service/books/D&D 5.0 - livro-do-jogador-2024.pdf` via PyMuPDF (not from memory) and cross-checked 1:1 against the book's own alphabetical talent table before seeding — generated by a one-off Python script (same pattern as `seed_items_5e.go`), not hand-typed. `ApplyASI` still doesn't cross-check the talento's own edition against the character's edition (a 5e character could technically be granted a 4e-flavored talento) — low priority since the UI's picker (`allTalentos5e` query) only ever offers 5e ones, this would only bite a direct API call.

- `domain.Character` carries both rule sets' fields simultaneously (e.g. `AntecedentID`/`Alignment`/`PersonalityTraits` are 5e-only, `Defense_*`/`SurgeValue` are 4e-only) rather than being split into subtypes — when adding character fields, follow this pattern and gate the logic by `character.Edition`, not the schema
- "Pericias" (5e skill proficiencies, e.g. Stealth/Perception) and "Talentos" (5e feats) are distinct from the older `Skill` model (4e-style class powers with `power_type`: at-will/encounter/daily/utility) — don't conflate the two systems
- `mod(attr int)` is THE ability-modifier formula (floor((score-10)/2), verified against the official "Valores e Modificadores de Atributo" table, p.44 of the 2024 Livro do Jogador) — used everywhere (HP, AC, saves, skills, spell DC). It used to be `(attr-10)/2` with no floor adjustment, which is wrong for every odd score below 10 (Go truncates toward zero, so `mod(9)` was `0` instead of the correct `-1`) — `armor_service.go` had an exact duplicate (`modifier()`) with the same bug; it now just delegates to `mod()`. If either ever gets "simplified" back to bare integer division, that reintroduces the bug — there's no compensating floor anywhere else.
- `CharacterService.Create()` fetches `domain.Class` via `ClassRepo.FindByID` **before** calling `recalculate()` — the handler only binds `class_id` from JSON, not the nested `Class` struct, so without this fetch `calcHP5e` silently computed initial HP as if `HitDie` were 0 (i.e. every new 5e character's starting HP was just `max(1, CON mod)`, regardless of class). `Update()` doesn't call `recalculate()` at all so it was never affected; `AddXP`/`LevelUp` load through `Repo.FindByID` (which preloads `Class`) so they were never affected either — this bug was isolated to character creation specifically.
- `Create()` fetches `domain.Race` the same way, for the same reason, and for a second one: `Character.Speed` has no input field anywhere in `CharacterCreate.tsx`'s form, so it always arrived at the handler as the zero-value. Before this fix it just stayed `0` forever — every 5e character exported "Deslocamento: 0" on the PDF sheet regardless of race. `Create()` now sets `character.Speed = race.Speed` for 5e characters right after loading the race (4e doesn't use this field, so it's untouched there). Found during a full audit of the 5e character-creation flow against the rulebook (`DND5E_CRIACAO_PERSONAGEM_CHECKLIST.md`), not from a user bug report — verified live via `/characters` create + GET across several races (30ft standard, 35ft Elfo da Floresta) before/after.
- Ability score assignment at character creation is **unconstrained free-form input** (1-20 per attribute, both in the Zod schema on the frontend and in the Go validation) — it does not implement or enforce the book's Point Buy (27-point budget, p.44) or Standard Array methods. This is a deliberate simplification already in place, not a bug, but worth knowing if asked to make character creation "rules-accurate." The values the player types are treated as **base scores, before** the Antecedent ability bonus below is added — see that section for how the final stored score is computed.
- **Armor selection at creation used to silently block submission if the player never touched the dropdown.** `CharacterCreate.tsx`'s armor `<select>` had a plain `<option value="">Sem armadura</option>` placeholder that was neither a real `Armor` catalog row nor ever assigned to the form via `setValue` — react-hook-form's Zod resolver would coerce that empty value, and the field would sit unresolved unless the player manually picked something from the real list. Fixed 2026-08-27: reused a pre-existing (but until then seed-code-orphaned — see below) `Armor` row named "Sem Armadura" (`armor_type: "none"`, `base_ac: 10`, `max_dex_bonus: -1`, i.e. CA = 10 + DEX with no cap) as the real default, removed the fake placeholder option, and added a `useEffect` that calls `setValue('armor_id', ...)` to that row's ID as soon as the armor list loads and nothing's been picked yet (`selectedArmorData` still `null`) — the player can still freely pick a different armor afterward, this only fills the gap when they don't. **The "Sem Armadura" row itself was a genuine, separate data-provenance bug**, unrelated to the frontend one: it already existed in the dev DB (created 2026-06-11) but no code in `seed_items_5e.go`'s `seedArmors5e` created or upserted it — meaning a fresh database (a real production reset, or any environment without that specific manually-created row) would have had *no* "no armor" catalog entry at all, silently reproducing the exact same creation-blocking bug this fix addresses. Added it to `seedArmors5e`'s upsert list so it's reproducible everywhere, not just in this one dev database.

### Mixed 2014/2024 ruleset (5e) — explicit user decision, not a default assumption
The user explicitly chose to run 2014 **and** 2024 content side by side rather than picking one edition, with a specific set of house rules (recorded here verbatim from that decision so future work doesn't re-litigate it):
1. **Golden rule of replacement:** if an element (spell, feat, class, item) exists in both books under the same name, the 2024 version always wins — never let a player pick the 2014 version of something just because it was stronger. This is a *content-curation* principle for whoever adds seed data later, not something enforced in code today (there's no automated "version conflict" detector) — when adding new spells/feats/subclasses, check whether a 2024 version already exists under that name before pulling in a 2014 one.
2. **Ability score bonus always comes from the Antecedent (2024 rules), never from the Race/Species** — this is true unconditionally, even for a player using a 2014-era species (e.g. Meio-Orc): they keep that species' *racial abilities* (like Resistência Implacável) but get zero ability-score bonus from it; their ability bonus still comes from whichever 2024 Antecedent they pick. Implementation: `domain.Race` has (and must keep having) no ability-bonus field at all — there is no "is this a 2014 or 2024 race" branch anywhere, because the answer is always "race gives zero ability bonus regardless." The actual mechanism lives on `domain.Antecedent`:
   - `Antecedent.AbilityBonusOptions` — JSON array of exactly 3 ability abbreviations (`FOR/DES/CON/INT/SAB/CAR`) from the book, e.g. `["INT","SAB","CAR"]` for Acólito.
   - `Antecedent.OriginFeatName` — the name of the one specific `Talento` (category "Origem") that antecedent grants — RAW 2024 doesn't let the player pick freely here, it's fixed per antecedent (e.g. Acólito → "Iniciado em Magia", Soldado → "Atacante Selvagem").
   - `Character.AbilityBonusChoice map[string]int` (`gorm:"-"`, creation-payload-only, e.g. `{"INT":2,"SAB":1}`) — the player's split among the antecedent's 3 options, validated in `CharacterService.applyAntecedentAbilityBonus` to be either +2/+1 across two of them or +1 across all three (nothing else), then added on top of the base scores in `Create()`. Missing/invalid choice is a hard 400 when the antecedent has bonus options — this is not optional for 5e antecedent-bearing characters.
   - After `Repo.Create()` succeeds, `Create()` looks up `OriginFeatName` via `TalentoRepo.FindByName(name, "5e")` and grants it automatically via `TalentoRepo.Add` — the player never manually picks this one from the general Talento list.
   - Frontend: `CharacterCreate.tsx` renders a "Bônus de Atributo" step right after Antecedent selection (5e only, only shown when the antecedent has `ability_bonus_options`) with a `+2 e +1` / `+1 nas três` mode toggle; `pendingItems` blocks submission until a valid choice is made.
   - **"Herói do Povo" (Folk Hero, 2014-only, not reprinted in the 2024 PHB's 16 core antecedents) resolved per the book's own rule, not by remapping it to a similar 2024 antecedent.** The 2024 PHB has an explicit sidebar for exactly this case — "Antecedentes e Espécies de Livros Antigos" (chapter 2, p.38, cross-referenced from chapter 4's antecedent intro): *"Antecedentes em livros antigos de D&D não incluem ajustes nos valores de atributo. Se você estiver usando um antecedente de um livro antigo, ajuste seus valores de atributo aumentando um valor em 2 e um valor diferente em 1, ou aumente três valores em 1 (...) Além disso, se o antecedente que você escolheu não fornecer um talento, você obtém um talento de Origem à sua escolha."* — i.e. keep the old antecedent as-is, don't substitute it, just make both choices free instead of fixed. Implemented as `Antecedent.IsLegacy bool`: when true and `AbilityBonusOptions` is empty, `applyAntecedentAbilityBonus` opens the ability choice to all 6 abilities (`FOR/DES/CON/INT/SAB/CAR`) instead of 3 named ones (same +2/+1-or-+1/+1/+1 validation); when true and `OriginFeatName` is empty, `Create()` requires `Character.OriginFeatChoiceID` (a `gorm:"-"` creation-payload field) referencing any Talento with `Category == "Origem"` and `Edition == "5e"`, validated and granted the same way. `seed_antecedents.go` marks "Herói do Povo" `IsLegacy: true` with both fields left empty; the other 4 pre-existing antecedents are normal 2024 entries, not legacy. Frontend: `CharacterCreate.tsx`'s "Bônus de Atributo" step shows all 6 abilities for a legacy antecedent instead of 3, and adds an Origin-feat picker (filtered to `category === "Origem"`) when there's no fixed one. The "+1 em três" mode is a genuine 3-of-N multi-select (`bonusTriple` state) rather than "all of `abilityBonusOptions"` — that distinction only matters for the 6-option legacy case (auto-applying +1 to all 6 would have been wrong).
   - **Update (2026-08-27): all 16 PHB 2024 antecedents are now seeded, not just 4.** The user flagged the missing 12 (Andarilho/Artesão/Artista/Charlatão/Eremita/Escriba/Fazendeiro/Guarda/Guia/Marinheiro/Mercador/Nobre) after seeing only 5 options in the creation UI. `seed_antecedents.go` was rewritten with all 16 core 2024 antecedents (plus "Herói do Povo" legacy = 17 total rows), every field (`AbilityBonusOptions`, `OriginFeatName`, `SkillProficiencies`, `ToolProficiencies`, `Equipment`, `Description`) extracted directly from `ai-service/books/D&D 5.0 - livro-do-jogador-2024.pdf` pages 183-204 via PyMuPDF (not from memory) — cross-checked antecedent-by-antecedent against the flavor-text paragraph on each page (not just position order, since the 2-column PDF layout doesn't extract in a consistent stat-stat-flavor-flavor vs stat-flavor-stat-flavor order page to page). This also caught **real errors in the original 4 (Acólito/Criminoso/Sábio/Soldado)**, which had 2014-edition content bled into what were supposed to be pure-2024 entries: Criminoso's skill proficiencies were wrong (`Furtividade`+`Enganação` seeded vs. the book's actual `Furtividade`+`Prestidigitação`), Acólito/Sábio had a `Languages` grant ("Dois idiomas à sua escolha") that doesn't exist anywhere in the 2024 background rules (only `ToolProficiencies` is granted, and both had it empty when it shouldn't have been), and all 4 had fully invented `Equipment` strings that didn't match the book's real (A)/(B) equipment package at all. All 16 non-legacy antecedents now correctly have `Languages: ""` (2024 backgrounds don't grant languages) and a real single tool proficiency. Verified: the 10 unique Origin feats already seeded in `seed_talentos_5e.go` (Alerta/Artifista/Atacante Selvagem/Curandeiro/Habilidoso/Iniciado em Magia/Músico/Sortudo/Valentão de Taverna/Vigoroso) exactly cover all 16 antecedents' `OriginFeatName` with no gaps and no new talento needed.
   - **`Feature`/`FeatureDescription` are now empty for all 16 core-2024 antecedents (only the `IsLegacy` 2014 ones keep a real 2014 feature)** — the 2024 PHB's background rules (p.183, "Um antecedente inclui as seguintes partes: Valores de Atributo, Talento, Proficiência em Perícias, Proficiência com Ferramentas, Equipamento") have no separate narrative "feature" beyond the granted Origin feat itself, unlike 2014's model (which had unique per-background features like Acólito's "Abrigo dos Fiéis" or Criminoso's "Contato no Crime" — all invented/2014-sourced text that the original 5-antecedent seed had kept even for the "2024" entries). `CharacterCreate.tsx` (background-selection card) and `CharacterDetail.tsx` (antecedent panel) both now guard that block behind `{bg.feature && (...)}` so nothing renders when it's empty, instead of showing an empty "✦ " heading.
   - **Update (2026-08-27, second pass): 3 more `IsLegacy` 2014 antecedents added — Artesão de Guilda, Forasteiro, Órfão — for 20 total.** The user pointed out (via a screenshot of a *different* PDF, `D&D 5.0 - livro-do-jogador-fundo-branco-biblioteca-elfica.pdf`, the 2014 PHB Brazilian translation, 315 pages — distinct from the 397-page 2024 file used everywhere else in this codebase) that more antecedents existed than the 17 seeded at the time. Extracted that file's full "Personalidades e Antecedentes" chapter (cap. 4, p.129-141) and cross-checked all 13 of its core backgrounds one by one against the golden-rule (same name → 2024 wins): Acólito, Artista, Charlatão, Criminoso, Eremita, Marinheiro, Nobre, Sábio and Soldado all share their exact name with a 2024 antecedent (2024 already wins for all 9, no import needed — verified their 2014 skill/tool lists too, not just the name, to be sure none secretly diverged in the underlying grant). Herói do Povo was already correctly imported as `IsLegacy`. That left exactly 3 with **no 2024 counterpart of the same name** — `Artesão de Guilda` (Intuição/Persuasão, distinct from 2024's differently-named, differently-skilled "Artesão"), `Forasteiro` (Atletismo/Sobrevivência — not present in 2024's 16 at all), and `Órfão` (Furtividade/Prestidigitação — also absent from 2024's 16) — added with their real 2014 skills/tools/equipment/feature text and `IsLegacy: true` (free ability-score choice across all 6 attributes, free Origin-feat choice), exactly mirroring the Herói do Povo pattern. **If asked to double-check antecedent completeness again, the systematic way to do it is this same one-by-one name-cross-check against both PDFs (2014 file's own chapter list vs. the 2024 file's 16), not spot-checking a handful — that's what let the first pass under-count by these exact 3.**
3. **Importing 2014-only subclasses:** allowed, as long as they weren't reprinted in 2024 — but always slot their features in at **level 3**, matching 2024's unified subclass-choice level, even if the 2014 book said level 1 or 2 for that class. This is already the convention every subclass entry in this codebase follows (see the Dual-edition logic section above) — no 2014-sourced subclass has been imported yet, but if one is, seed it at level 3 regardless of what the source book says.
4. **DM-side monsters/magic items from 2014 books** work as-is against 2024 characters, no conversion needed — **not applicable to this codebase**, there is no `Monster` domain model and no mechanical Weapon Mastery system that an old weapon would need retrofitted onto it, so this rule has nothing to implement against today.
- `SkillRepository.FindByLevel(classID, level)` filters `level = ?` (exact), not `level <= ?`. It used to be `<=`, and `checkAndApplyLevelUps`/`LevelUp` call it once per level gained inside their level-up loop — with `<=`, every level up re-fetched *all* skills from level 1 up to the new level and re-`AddSkill`'d them all, which silently granted the **non-chosen** option of every level-1 `RequiresChoice`/`ChoiceGroup` pair (e.g. picking "Virtude da Astúcia" at creation, then reaching level 2, would also add "Virtude da Bravura") the moment a character leveled past 1. Fixed by matching the exact level, plus both call sites now skip any `skill.RequiresChoice` result defensively — today no seeded skill has `RequiresChoice: true` above level 1 (all choice groups across every class/race are resolved once, at creation, via `CharacterCreate.tsx`'s `choiceSelections`), so the skip is a no-op currently, but it stops a future above-level-1 choice skill from being auto-granted on both sides instead of surfacing a real choice UI (which doesn't exist yet for level-up, only for creation). Verified with a live API test: create a 4e Bardo, choose one `virtude_bardo` option, grant enough XP to reach level 5 through multiple ASI pauses, confirm the unchosen option never appears in `character.skills`.

### Shop / equipment / currency (5e)
`domain.Character` carries the 5 official 5e coins as independent int fields (`CopperPieces/SilverPieces/ElectrumPieces/GoldPieces/PlatinumPieces` — never auto-converted into each other except during a purchase, see below). `domain.Item` is the shop catalog (armas/equipamento/item_magico — armor is **not** duplicated here, it stays on the pre-existing `domain.Armor`, which gained `Weight`/`CostCopper` fields for this feature). `internal/seed/seed_items_5e.go` (generated once via a Python script from the Livro do Jogador 2024's Chapter 6 tables, not hand-typed) seeds ~38 weapons + ~92 adventuring-gear items + 13 armors (the `Armor` table was completely empty before this — a pre-existing gap this closed as a side effect) + a **curated, non-exhaustive** set of ~22 magic items. Magic items have no fixed price in the actual 5e rules (Xanathar's Guide gives a dice-roll price *range* per rarity for the DM to negotiate) — `CostCopper` for those is the average of that range, a deliberate simplification to make direct purchase possible; don't treat it as RAW.

`internal/service/inventory_service.go` (`InventoryService`, constructed directly from `*gorm.DB` like `BackgroundService`/`AntecedentService`, no repository layer) owns all currency math: `totalCopper()` converts the 5-coin purse to a canonical copper value (1 sp=10cp, 1 ep=50cp, 1 gp=100cp, 1 pp=1000cp) and `copperToPurse()` "melts and remakes change" — every purchase re-denominates the *entire* remaining purse into the fewest/highest-value coins, it does not preserve which specific coins were spent. `PurchaseItem`/`PurchaseArmor` (in `internal/handler/inventory_handler.go`, routes `POST /characters/:id/shop/items/:item_id` and `.../shop/armors/:armor_id`) require the requester to own the character (404 if not, same not-found-not-forbidden pattern as `ExportPDF5e`). `SetCurrency` (`PATCH /characters/:id/currency`) is the "Mestre concede ouro" mechanic — it's gated on `userRole == domain.RoleMaster` only, **not** on any character/campaign relationship (there is no campaign/group model in this codebase — a master can set the currency of any character in the system). It sets absolute totals, not a delta. Frontend: `pages/Shop.tsx` (route `/characters/:id/shop`, linked from a 5e-only "🛒 Loja" button in `CharacterDetail.tsx`) and `components/InventoryPanel.tsx` (currency + owned-items display on the character page).

- **"Sem Armadura" catalog row and its `armor_type` values are also relevant to the Shop/`domain.Armor` picture above** — see the Character creation section below for the 2026-08-27 fix that made it a reliable seeded default instead of an orphaned manual row.

### Spellcasting (5e) — phase 1, added 2026-08-27
The codebase had **no spell system at all** until this pass (this was explicitly called out as a known gap in the PDF export section below, and in the class-progression audit above) — no spell catalog, no per-character known/prepared spells, no spell-slot table. The user asked for the spell system specifically as the first phase of a larger creation-flow overhaul (equipment browsing, tabbed creation UI, and a fully computed character sheet are later phases, not yet started as of this writing).

**What exists now:**
- `domain.Spell` (table `spells`): `Name`, `Edition`, `Level` (0 = truque, 1-9 = círculo), `School`, `Ritual bool`, `Concentration bool`, `Classes` (JSON `{"ClassName": circleLearnedAt}`, since one spell is shared across several classes' lists rather than duplicated per class), `Description` (currently empty for all 397 rows — see the gap noted below). `Character.Spells []Spell` is a `many2many:character_spells` association, following the exact same pattern as `Talentos`/`character_talentos` — `SpellRepository`/`SpellService`/`SpellHandler` mirror `TalentoRepository`/`TalentoService`/`TalentoHandler` file-for-file (`GetAll(edition)`, `GetByCharacter`, `Add`, `Remove`). Routes: `GET /spells?edition=5e` (public), `GET/POST/DELETE /characters/:id/spells[/:spell_id]` (protected, same shape as the talentos routes).
- **`internal/seed/seed_spells_5e.go` (397 spells) was generated by a one-off Python script from the "Lista de Magias de X" sections inside each class's own description in the PHB 2024's Classes chapter (cap. 3, pages 55-182) — not from the standalone "Magias" chapter (cap. 7, pages 241-375), which turned out to contain only the general spellcasting *rules* text plus the alphabetical spell *descriptions*, no per-class breakdown.** Each of the 8 casting classes (Bardo/Bruxo/Clérigo/Druida/Feiticeiro/Guardião/Mago/Paladino) has its own "Lista de Magias de X" section (bounded from that heading to the next "Subclasses de X" heading) listing every spell it knows as repeating `Nome / Escola / Especial` triples, where `Especial` is `—`, or some comma-separated combination of `C` (Concentração), `R` (Ritual), `M` (componente Material). The parser is a small state machine (not a fixed group-of-3-lines split) because spell names sometimes wrap across 2 physical lines in the PDF's text extraction (e.g. "Mansão Magnífica de\nMordenkainen") — a naive fixed-3-line grouper desyncs permanently after the first wrapped name; the state machine instead scans forward accumulating name lines until it hits a line that's an exact match for one of the 8 known school names, then expects a special-flags line next. Guerreiro/Ladino/Monge have no section of their own (correct — Guerreiro's Cavaleiro Místico and Ladino's Trapaceiro Arcano subclasses draw from Mago's list instead, and Monge doesn't cast). Verified spot-checks against well-known spells (Bola de Fogo = Evocação/3º círculo/Feiticeiro+Mago, Detectar Magia = Adivinhação/1º círculo/C,R/all 8 classes, Palavra de Poder: Matar = Encantamento/9º círculo/Bardo+Bruxo+Feiticeiro+Mago) all matched exactly.
- **Full mechanical spell descriptions (damage dice, exact range/area, full effect text) were deliberately NOT seeded in this pass** — `Description` is empty for all 397 rows. Getting name/circle/school/ritual/concentration/class-list right was enough to build the character-creation picker and the known-spells display; the ~135-page "Descrições das Magias" alphabetical section (cap. 7) with the full text per spell is a separate, much larger extraction task, deferred the same way sub-catalogs like Bruxo's Invocações Místicas or Mestre da Batalha's maneuvers were deferred during the class-progression pass — flag this explicitly if a future task assumes spell descriptions exist.
- **Spell slot progression (`internal/service/character_service.go`):** `fullCasterSlots5e` (Bardo/Clérigo/Druida/Feiticeiro/Mago) and `halfCasterSlots5e` (Paladino/Guardião) are `[21][]int` tables indexed by character level, each element `[espaços 1º círculo, 2º, ...]`. `pactMagicSlots5e`/`pactMagicCircle5e` cover Bruxo's separate Magia de Pacto mechanic (short-rest recovery, all slots always the same, level-scaling circle). **Important 2024 PHB change verified against the actual extracted table, not assumed from 2014 memory: Paladino and Guardião now get their first spell slot at character level 1, not level 2 like in the 2014 PHB** — confirmed by reading the raw "Características de Paladino"/"Características do Guardião" tables directly (`Nível 1: ... Espaços de Magia: 2` for both), cross-checked at levels 9 and 13 too before trusting the rest of the table shape (which otherwise matches the well-known unchanged-since-2014 half-caster progression, just shifted one level earlier). `cantripsKnown5e(className, level)` covers the "base cantrips at level 1, +1 at level 4, +1 at level 10" pattern shared by all 6 cantrip-having classes (Guardião/Paladino get none, matching RAW). These tables are **duplicated in `frontend/src/lib/spellSlots.ts`** (`spellSlotsFor`/`pactMagicFor`/`cantripsKnownFor`) — same justified duplication pattern already established for `xpTables.ts`, needed because frontend and backend don't share a runtime; if either table is ever corrected, fix both copies.
- **Character creation (`CharacterCreate.tsx`):** a new "Magias e Truques" step appears only for 5e characters whose selected class is a caster, after Atributos/HP (so the ability-score-based counts are already known — though this uses the player's *base* attribute values, not final values after the Antecedent bonus, as a deliberate simplification). It shows exactly the right number of cantrips (`cantripsKnownFor`) and 1st-circle spells to pick (`spellsToPickAtLevel1` — a local helper distinct from the generic "prepared caster" formula because Bardo/Bruxo/Feiticeiro have a fixed spells-known count at level 1 (4/2/2) unrelated to their ability modifier, and Mago's count (6) reflects the Grimório's starting size from its own `Conjuração de Mago` feature text, not the smaller "spells prepared" count), filtered from `GET /spells?edition=5e` by checking the class's own key in each spell's `Classes` JSON. Selections block submission via the existing `pendingItems` mechanism (same pattern as talentos/pericias) and are attached with sequential `POST /characters/:id/spells/:spell_id` calls after `characterService.create()` succeeds, mirroring exactly how selected talentos are already attached post-creation.
- **`CharacterRepository.FindByID` needed `.Preload("Spells")` added** — same exact gap as the pre-existing "Talentos preload missing" bug documented elsewhere in this file; without it, `GET /characters/:id` silently returned `spells: null` even though the join-table rows existed. Found live: a test character had 9 rows in `character_spells` but `spells` came back empty on the full character fetch until this was added.
- **`CharacterDetail.tsx`** shows a "Magias e Truques" panel (only when the character has any) grouping known spells into Truques and per-circle sections, plus a computed spell-slots/pact-magic readout in the panel header via the same `spellSlots.ts` helpers.
- **Not done in this phase, tracked as follow-ups, not silently forgotten:** no "prepare/unprepare" distinction (everything added via the picker is just "known", full stop — real 5e distinguishes known vs. prepared for several classes, simplified away here same as this codebase already does for other subsystems); no level-up flow for learning new spells past level 1 (the ASI/level-up engine doesn't touch spells at all yet); no spell descriptions (see above); no tabbed character-creation UI yet (the "Equipamento Inicial" area below is phase 2 of the same request; tabs and the fully-computed final sheet are still not started).

### Equipamento Inicial de Classe (5e) — phase 2, added 2026-08-27
Second phase of the same creation-flow overhaul that started with spellcasting above. The book's "Equipamento Inicial" row (Livro do Jogador 2024, cap. 3, tabela "Traços Básicos de X" of each of the 12 5e classes) was extracted verbatim from the PDF (not from memory) for every class and turned into real, structured, pickable data instead of descriptive text — this was a deliberate step up from the pattern used for `Antecedent.Equipment` (plain string), because the user explicitly asked to see the actual attack bonus/AC each option grants, which requires resolving real `Item`/`Armor` catalog rows, not just displaying text.

**Schema:** `domain.ClassEquipmentOption` (`ClassID`, `Edition`, `OptionLabel` "A"/"B"/"C", `GoldPieces`) has many `domain.ClassEquipmentComponent` (`OptionID`, `ItemID *uint` XOR `ArmorID *uint` XOR `ExtraText`, `Quantity`). Every class has exactly 2 lettered options (Guerreiro has 3) — pick the itemized package, or trade it all for a flat PO amount; some itemized options also include a small leftover-change PO amount alongside their items, which is why `GoldPieces` exists on every option, not just the pure-gold ones. `ExtraText` exists only for two book-level "your choice, no single catalogable item" cases: "Instrumento Musical à sua escolha" and "Ferramentas de Artesão à sua escolha" (17 variants in the book — cataloging all of them was out of scope) — same simplification precedent as `Antecedent.ToolProficiencies` being a free-text hint elsewhere in this codebase.

**Catalog gaps found and fixed while cross-referencing the extracted equipment text against the existing `seed_items_5e.go` catalog:** three items the book's class equipment packages reference by exact name didn't exist in the item catalog at all (a real pre-existing gap in the Chapter 6 seed, not something this feature caused) — added `Ferramentas de Ladrão` (Thieves' Tools, 25 po), `Kit de Herbalismo` (Herbalism Kit, 5 po — distinct from the already-seeded `Kit de Curandeiro`/Healer's Kit, which is a different tool), and `Livro de Magias` (Spellbook, 50 po — distinct from the generic `Livro`). All three prices are the book's real listed cost, not invented.

**Backend:** `internal/repository/class_equipment_repository.go` + `internal/service/class_equipment_service.go` + `internal/handler/class_equipment_handler.go` (thin, same shape as every other read-only catalog handler) expose `GET /classes/:id/equipment-options` (public), preloading `Components.Item`/`Components.Armor` so the frontend gets full item/armor data (weight, cost, and for weapons the `Description` text with dice/damage-type/properties already embedded — see `seed_items_5e.go`'s weapon rows) in one call. `internal/seed/seed_class_equipment_5e.go` resolves every component by name at seed time via new `getItem5e`/`getArmor5e` helpers (fail loud via log if a name doesn't match, so a typo shows up immediately in the seed log instead of silently vanishing) and is idempotent (deletes and rebuilds an option's components on every boot, matched by class+edition+label).

**Character creation grant:** `Character.EquipmentOptionID *uint` (`gorm:"-"`, creation-payload-only, same pattern as `OriginFeatChoiceID`) is optional — if the player doesn't choose one, nothing is granted, same as before this feature existed. `CharacterService.grantStartingEquipment()` (called from `Create()` after the character row exists) validates the option belongs to the chosen class, then upserts each component into `CharacterItem`/`CharacterArmorOwned` (same add-quantity-if-exists logic as `InventoryService.PurchaseItem`/`PurchaseArmor`, just without the gold deduction since this is a grant, not a purchase) and adds `GoldPieces` onto `Character.GoldPieces`. Verified live end-to-end: created a 5e Guerreiro choosing option B, got exactly Armadura de Couro Batido + Cimitarra + Espada Curta + Arco Longo + 20 Flechas + Aljava + Kit de Explorador de Masmorras + 11 PO in the character's inventory — matches the book's option B exactly.

**Frontend (`CharacterCreate.tsx`):** a "Passo 10.5 — Equipamento Inicial" section (same non-integer step-numbering precedent as the existing "Passo 4.5", so the later steps didn't all need renumbering) appears for 5e only, right after Armadura, showing every option as a selectable card. `lib/weaponParser.ts` parses a weapon `Item.Description` string (there's no separate structured damage/property field on `domain.Item` — it all lives in that one text field, see the Shop section above) into dice/damage-type/finesse/ranged, and computes a live attack-bonus/damage preview using the player's current Força/Destreza field values and a hardcoded +2 (level-1 proficiency is always +2, and starting-equipment weapons are always ones the class is proficient with by construction) — ranged (`Munição`) weapons use DES, finesse (`Acuidade`) weapons use whichever of FOR/DES is better, everything else uses FOR. Armor components show computed AC via the same `max_dex_bonus` logic used elsewhere (`acFor()`). The choice is optional (not enforced via `pendingItems`), consistent with the backend making it optional. **Not wired up:** picking an option that includes armor does not auto-populate the separate Armadura dropdown (`armor_id`, the character's *equipped* armor) — the two stay independent; picking Guerreiro's option A grants a Cota de Malha into inventory but the player still separately chooses what's equipped. This was a deliberate scope boundary given the size of the feature, not an oversight — flag it if a report comes in about "I picked plate mail in equipment but my sheet shows no armor bonus."

### Frontend structure
Flat structure, no feature folders: `pages/` (routed screens), `components/` (shared UI), `services/` (one Axios-based module per backend resource, all importing the shared `services/api.ts` client), `store/authStore.ts` (Zustand, persists `token`/`user` to `localStorage`), `types/index.ts` (shared TS types). Routing is in `App.tsx` via `react-router-dom`; all routes except `/login` and `/register` are wrapped in `PrivateRoute`, which checks `useAuthStore`. `services/api.ts` attaches the JWT to every request, force-logs-out on 401, and shows a "waking up server" toast if a request takes >4s (the backend is hosted on a free tier with cold starts).

The visual language is a dark/gold "RPG" theme: Tailwind v3 with a custom `rpg` color palette and `font-rpg` (Georgia serif) defined in `tailwind.config.js`, plus reusable classes (`.btn-rpg-primary`, `.rpg-card`, `.rpg-input`, etc.) in `src/index.css`. `shadcn/ui` is the base component library going forward (forms/dialogs/cards/inputs) — scaffolding lives in `components.json`, `src/lib/utils.ts` (`cn()` helper), `src/components/ui/`, with the `@/*` → `./src/*` path alias configured in both `vite.config.ts` and `tsconfig.app.json`; shadcn's semantic color tokens (`--primary`, `--border`, etc., in `src/index.css`) are mapped onto the existing gold palette rather than shadcn's default neutral one, so new components already match the theme. Existing pages were not migrated to shadcn components in this pass — only new UI uses it.

### "Meus Personagens" dashboard
`CharacterList.tsx` (route `/characters`) was redesigned around a reference mockup: a sidebar (`components/CharacterCard.tsx` holds the per-character card; the sidebar nav itself is inline in the page) with only the nav items that have a real page today (`/` and `/characters` — the mockup's Campanhas/Inventário/Biblioteca/Mapas/Configurações items were deliberately left out, not just hidden-but-present, since those pages don't exist), a header with a working client-side name search, and a "Resumo" side panel that shows only the real character count — no fabricated Campanhas/Conquistas/Itens numbers, and no "Atividade Recente" feed, since there's no activity-log model in the domain to back either one (a simple `ActivityLog` model populated at level-up/character-creation time would be the natural way to add that later). Each `CharacterCard` gets a deterministic accent color (by `character.ID`) and a themed corner-ornament frame that lights up on hover. XP-bar math (`currentLevelXP`/`nextLevelXP`/progress %) is shared between this card and `CharacterDetail.tsx` via `src/lib/xpTables.ts` — don't reintroduce a second copy of the XP tables.

### Welcome screen and level-up celebration
A one-time welcome modal (`components/WelcomeModal.tsx`) shows after a player's very first login following registration, never again after — including from a different browser/device, so the flag lives on `domain.User.WelcomeSeen` (bool, default false), not `localStorage`. `PATCH /users/me/welcome-seen` (`AuthHandler.MarkWelcomeSeen`, behind `AuthMiddleware`) flips it; `Register`/`Login` responses already include `welcome_seen` on the `user` object. `CharacterList.tsx` reads `user.welcome_seen` from `useAuthStore` to decide whether to render the modal, and on dismiss calls `authService.markWelcomeSeen()` (backend) plus the store's `markWelcomeSeen()` (optimistic local update, also re-persisted into the `user` cached in `localStorage`). Note: this field defaults to `false` for every pre-existing user too (no backfill script), so anyone who already had an account before this migration will see the welcome modal once on their next login. `components/LevelUpCelebration.tsx` is a similar animated overlay (gold particle burst) triggered from `CharacterDetail.tsx` whenever any of the three level-up paths (`addXP`, `applyASI`, manual `LevelUp`) report a level change — it's additive to, not a replacement for, the existing text-banner XP feedback.

### Avatar storage, edition badge, and rumors
`character.AvatarURL` holds a full `data:<mime>;base64,<...>` URI stored directly in the Postgres row, not a path to a file on disk. It used to save to local `./uploads/` and store just `/uploads/<filename>`, but that directory is **not persistent** across backend restarts/redeploys (free-tier hosting) — the DB would still point at a filename that no longer existed, showing as a broken image. `UploadHandler.UploadAvatar` (`upload_handler.go`) now reads the multipart file into memory, base64-encodes it, and writes the data URI straight onto the character (capped at `maxAvatarBytes` = 2MB original file size, checked before reading); there's no dedicated storage service (S3/Cloudinary/etc.) involved or needed for this. `r.Static("/uploads", ...)` was removed from `main.go` since nothing serves from that path anymore. Frontend (`CharacterCard.tsx`'s `resolveAvatarSrc`, `AvatarUpload.tsx`'s `buildUrl`) checks for the `data:` prefix and uses the value as-is in that case, only prefixing `API_BASE`/`API_URL` for old-style relative paths (which will 404 and fall through to the placeholder emoji via each `<img>`'s `onError` — there's no migration for pre-existing broken avatar rows, they just show the fallback until re-uploaded).

`CharacterCard.tsx` shows a small "D&D {edition}" pill in the top-left corner of the portrait so 4e vs 5e is visible from the list view without opening the character (the detail page already showed this as plain text under the name).

Rumors ("boatos que circulam sobre o personagem") live on `Character.Rumors` — edition-agnostic free text, not part of the 5e-only `PersonalityTraits`/`Ideals`/`Bonds`/`Flaws` block. It's exposed through the same allowlisted-fields `GET/POST /characters/:id/background` route as those four (`BackgroundService.Get`/`Save` in `background_service.go` — despite the route name, this endpoint edits fields directly on `Character`, unrelated to the `domain.Background` struct, which is actually the antecedent-style catalog model, not the notes system), and rendered as an extra field in `components/BackgroundForm.tsx`. Fixing this surfaced a real pre-existing bug worth knowing about: `CharacterDetail.tsx` was instantiating `<BackgroundForm characterID={...} />` **without** the `background` prop, so the form always started in edit mode with every field blank — opening a character's page and clicking "Salvar" without retyping anything would silently wipe `personality_traits`/`ideals`/`bonds`/`flaws` back to empty strings (the read-only "Personalidade" panel elsewhere on the same page reads `character.*` directly, so it never showed this — the bug was isolated to `BackgroundForm`). Now fixed by passing `background={{ history: '', personality_traits: character.personality_traits ?? '', ... }}` from `CharacterDetail.tsx`. Note `history` in that same form has never actually persisted — `BackgroundService.Save`'s allowlist doesn't include it — that's pre-existing and out of scope here, not something this pass introduced.

### PDF export (5e)
A 5e-only "Exportar ficha PDF" button (`CharacterDetail.tsx`, gated on `character.edition === '5e'`) hits `GET /characters/:id/export/pdf`. The Go handler (`ExportPDF5e` in `character_handler.go`) checks `character.UserID == c.GetUint("userID")` (404 if not, to avoid leaking existence of other users' characters) — most other character endpoints in this codebase do **not** enforce ownership today, so don't copy this handler as evidence that they do. It does 100% of the D&D rules computation via `service.BuildPDF5eExportPayload`, then fills the AcroForm **directly in Go** via `internal/pdfexport.FillCharacterSheet5e` — no other service involved.

**This used to go through the Python ai-service over HTTP (`POST /export/pdf/5e`, base URL from `AI_SERVICE_URL`) — that path is gone from production and shouldn't be resurrected as "the fix" if export breaks again.** The ai-service was only ever run locally; it was never deployed anywhere, so on the actual hosted backend this call always failed with a 503 ("Serviço de exportação de PDF não está disponível no momento"), 100% of the time, for every user, forever — confirmed directly from production logs (every `GET .../export/pdf` returning 503). Moving the fill step into Go removes the cross-service dependency entirely: the template PDF and the field map are embedded into the Go binary via `go:embed` (`internal/pdfexport/assets/`), so export works wherever the already-deployed backend runs, no second service, no extra hosting, no new env var to configure.

**How the Go fill works (`internal/pdfexport/pdfexport.go`):** uses `github.com/pdfcpu/pdfcpu` (pure Go, no cgo, no external binary) via `api.FillForm(io.ReadSeeker, io.Reader, io.Writer, conf)`, which takes the source PDF, a JSON payload describing field values, and writes the filled PDF — all in memory, no temp files. pdfcpu's fill JSON format requires each field's internal AcroForm object ID (not just its name) — those IDs can't be reconstructed by hand, so `internal/pdfexport/assets/form_skeleton.json` is a **frozen one-time export** of the template's full field list (210 text fields + 124 checkboxes, `id`+`name`+empty `value`) produced once via `api.ExportFormJSON` against the real template. At request time, `FillCharacterSheet5e` loads that skeleton, looks up each field it needs to set *by name*, mutates just those entries' `Value`, and feeds the whole thing back to `FillForm`. If the template PDF is ever replaced, `form_skeleton.json` must be regenerated the same way (`api.ExportFormJSON` against the new file) — the frozen IDs are specific to that exact PDF's object graph.
- pdfcpu has a documented open issue for checkbox filling on *some* PDFs ("corrupt form field: missing entry AP") — this was checked against **this specific template**, not assumed away: a real fill was rendered with PyMuPDF and both text and checkboxes appeared correctly, so the issue doesn't affect this file. Re-verify visually the same way if the template PDF changes.
- `dnd5e_pdf_field_map.json` (embedded copy, same content as `ai-service/pdf_export/reference/dnd5e_pdf_field_map.json`) is unchanged — see the field-map gotcha below, it still applies.
- `internal/pdfexport/pdfexport_test.go` is the project's first Go test file. It fills a synthetic character (specific known trained/untrained skills) and re-exports the form from the *output* PDF via `api.ExportForm` to assert on the real filled values — this is the automated version of the manual regression check below; run `go test ./internal/pdfexport/...` after touching anything in this package or the field map.
- **The Python side (`ai-service/pdf_export/fill_dnd5e_sheet.py`, its FastAPI route, and `ai-service/tests/test_export_pdf_5e.py`) is left in place but is no longer live for anything** — it was the original implementation this was ported from, kept only as a secondary reference for the field mapping (its own tests still pass and still document the same checkbox-scramble fix). Don't add features to it expecting them to reach production; add them to `internal/pdfexport` instead.

**Field-map gotcha, read before touching this:** the template PDF (embedded copy of `ai-service/books/D&D 5.0 - ficha-de-personagem-completavel-biblioteca-elfica.pdf`) is a community PT-BR translation. Its skill-row AcroForm widgets (text field + proficiency checkbox) were **not** moved when the printed labels were re-sorted alphabetically in Portuguese — the widgets are still in the original template's English-alphabetical row order (Acrobatics, Animal Handling, Arcana, Athletics, Deception, History, Insight, Intimidation, Investigation, Medicine, Nature, Perception, Performance, Persuasion, Religion, Sleight of Hand, Stealth, Survival), while the *visible* Portuguese label at that same row follows a different (Portuguese-alphabetical) order. E.g. the field literally named `"Perception"` renders on the row printed "Medicina". The field map's `pericias` list already encodes the corrected pairing (verified by rendering a self-labeled PDF with PyMuPDF and reading it visually, not by assumption) — if the template PDF is ever replaced, redo that visual verification instead of trusting field names, and re-check the ability-save block and header fields too (those happened to already be correctly positioned in this template, but that was verified, not assumed).

**Frontend error surfacing:** `handleExportPdf` (`CharacterDetail.tsx`) requests the export with `responseType: 'blob'` (since a successful response is the PDF itself) — this means axios delivers an *error* response's body as an unparsed `Blob` too, not as parsed JSON. It used to have a bare `catch { setExportPdfError('genérico...') }` that discarded the real error entirely, so every failure showed the exact same "tente novamente em instantes" with no way to tell them apart. Fixed via `extractExportPdfErrorMessage()`, which reads the blob as text, `JSON.parse`s it, and surfaces the backend's actual `error` field — falling back to the generic message only if the body truly isn't JSON. If a report of a failed export comes in again, read the message shown on screen first; with the ai-service dependency gone, a real failure now means an actual bug in `pdfexport` (check the `error` detail), not an infra/reachability problem.

**Coverage expansion — physical description, backstory, synthesized Features/Traits, avatar stamp, Player Name (all edition-agnostic domain fields, 5e-only PDF usage):** `domain.Character` gained `Age`/`Height`/`Weight`/`Eyes`/`Skin`/`Hair`/`History` (all `string`), editable through the existing `/characters/:id/background` route — `internal/service/background_service.go`'s `allowedBackgroundFields` now includes all of them, plus `history` itself, which fixes a **pre-existing bug** where `History` was rendered in `BackgroundForm.tsx` but silently never persisted (missing from the old inline allowlist). Frontend: `BackgroundForm.tsx` gained a "🧍 Aparência Física" grid (age/height/weight/eyes/skin/hair, both edit and read-only modes); `CharacterDetail.tsx`'s `<BackgroundForm background={{...}} />` call and `types/index.ts`'s `Character`/`Background` interfaces were extended to match — `character.age` etc. now come straight off the character object returned by `GET /characters/:id`, not a separate fetch.
- **"Features and Traits" (page 1) is synthesized, not stored verbatim anywhere:** `buildCaracteristicasHabilidades()` in `pdf_export_service.go` walks `character.Skills` (grouping by `IsClassFeature`/`IsRaceFeature`) and `character.Talentos`, and formats them into a labeled text block ("CARACTERÍSTICAS DE CLASSE: ...", "TRAÇOS RACIAIS: ...", "TALENTOS: ..."). It only reflects what's actually seeded/granted on that character — at level 1 with no subclass chosen yet (subclasses seed at level 3, see Dual-edition logic above) and for classes/races with no `Skill` rows flagged as features, sections legitimately come out empty; that's the existing shallow depth of the 5e seed data showing through, not a bug in the synthesis. `CharacterRepository.FindByID` (`class_repository.go`, despite the filename) needed `.Preload("Talentos")` added — it was preloading `Skills` but not `Talentos`, which would have silently dropped the Talentos section.
- **Player Name (`PlayerName` field, distinct from the character's own name) comes from the account owner, not the character:** `ExportPDF5e` (`character_handler.go`) now looks up `domain.User` by `character.UserID` via the handler's new `UserRepo` field (wired in `main.go`) and passes `user.Name` into `BuildPDF5eExportPayload`'s new `playerName` parameter — every call site of that function needed updating for the new signature.
- **Avatar photo on page 2 ("APARÊNCIA DO PERSONAGEM") is stamped as a post-fill image watermark, not a normal field value:** that AcroForm widget (`CHARACTER IMAGE`, PDF Rect `[36.4791, 443.398, 199.172, 661.497]`, documented in the field map's `imagem_personagem` block) is a **pushbutton field** (`/FT /Btn` with the Pushbutton flag) — pdfcpu's `fillBtn` explicitly no-ops for pushbuttons, so there is no way to put an image into it via the normal fill-JSON mechanism. `applyAvatarImage()` in `pdfexport.go` instead: decodes `character.AvatarURL`'s `data:` URI (already base64 in the DB, see Avatar storage section above), reads pixel dimensions via `image.DecodeConfig` (blank-imports `image/png`, `image/jpeg`, `golang.org/x/image/webp` to register decoders), computes a contain-fit scale (`min(targetW/imgW, targetH/imgH)`, centered — **not** stretched to fill, so portrait/landscape photos never distort), writes the image to a temp file (pdfcpu's `api.ImageWatermark` is file-path-only), and applies it via `api.AddWatermarksMap` scoped to just that one page. Every step fails soft (returns the un-stamped PDF unchanged) rather than erroring the whole export — a character with no avatar, or a corrupt/undecodable image, still gets a complete PDF minus the photo. `scale ... abs` in pdfcpu's watermark description string is a multiplier of the image's **native pixel width**, not a target size in points — don't reintroduce the earlier mistake of treating it as "target width," which rendered the photo ~200x oversized.
- Verified end-to-end (not just unit-tested in isolation): created a real 5e character via the live API with a non-trivial Antecedent (Acólito, ability bonus + auto-granted Origin Feat), saved all the new background fields, uploaded a real generated PNG as avatar, exported, and rendered the actual output PDF pages to PNG with PyMuPDF to visually confirm — Nome do Jogador, Idade/Altura/Peso/Olhos/Pele/Cabelos, História, the synthesized Talentos line, and the contained/centered avatar photo all appeared correctly positioned. Long values (e.g. "Guilherme Testador", "Negros, presos em tranças") visually clip at the fixed-width AcroForm field boundary in some PDF viewers — that's the template's own fixed field width/font size, not a bug introduced here; not addressed since the template isn't being redesigned.
- **Still not addressed** (tracked in the field map's `nao_preenchido_v1` block, not silently forgotten): weapon attack rows (`Wpn Name`/`AtkBonus`/`Damage` x3), the CP/SP/EP/GP/PP currency breakdown on page 1 (the character *has* this data — `Character.CopperPieces` etc., see Shop section — it just isn't wired into the export payload yet), `Equipment`/`ProficienciesLang` text blocks, `Inspiration`, and page 2's `Allies`/`FactionName`/`Feat+Traits`/`Treasure`/`Faction Symbol Image`. **All of page 3 (spellcasting: `Spells 1`-`Spells 9` slot fields, `SpellcastingAbility`/`SpellSaveDC`/`SpellAtkBonus`, known/prepared spell lists) is still unaddressed in the PDF export specifically** — **but the underlying gap this note originally described (no spell domain model at all) is closed as of 2026-08-27**, see the "Spellcasting (5e)" section below: `domain.Spell`, `Character.Spells`, and the level-1 spell-slot tables now exist and are wired into character creation and the character detail page. Wiring page 3 of the PDF is now "map an existing model onto fields" rather than "design a subsystem from scratch," but still needs the actual mapping work (and full spell mechanical descriptions, not yet seeded — see that section) before it can be done.

### Deployment
Frontend deploys to Vercel (SPA rewrite in `frontend/vercel.json`); backend is expected to be a separately hosted service (CORS in `main.go` explicitly allowlists `http://localhost:5173` and `https://rpg-manager-smoky.vercel.app` — update this list, not a wildcard, when adding origins).

**"Acordando o servidor..." cold-start toast (`frontend/src/services/api.ts`):** had a real concurrency bug — it tracked a single shared `slowTimer` variable per Axios interceptor, but the app routinely fires several requests in parallel (e.g. opening a character page fetches the character, pericias, talentos, and inventory at once). Each new request's interceptor overwrote the previous request's timer reference, so a fast request finishing could clear a *different*, still-pending request's timer — the toast could fail to show, show and never hide, or hide while another request was still loading. Fixed 2026-08-27 by switching to an in-flight request counter (`pendingRequests`): the "slow" timer is armed only when the count goes 0→1, and the toast is dismissed only when the count returns to 0, regardless of how many requests overlap. **Whether this toast is still needed at all is an open question, not yet resolved** — it was written for Render's free-tier backend cold start (30-60s), and the user has since indicated the database moved to Neon; that's a different service (Postgres, not backend hosting) with its own separate compute-suspend behavior (typically ~1-2s, not 30s), so it doesn't by itself confirm whether the *backend web service* still cold-starts the way this toast assumes. Don't remove or re-tune the 4s/"até 30s" copy without first confirming current hosting for the Go backend itself (not just the DB) with the user.
